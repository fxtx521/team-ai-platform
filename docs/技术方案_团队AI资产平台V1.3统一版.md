# 团队 AI 资产平台 技术方案 V1.3（Mac/Win 统一版）

日期：2026-10-22 ｜ 状态：响应老板"Mac 和 Win 必须统一"硬约束的架构定稿

## 〇、本版核心变化（相对 V1.2）

V1.2 的"双端并存+契约统一"被否决——那是大厂养得起的玩法，20 人团队养两套客户端必然漂移。
V1.3 改为**单一执行器架构**：一个代码库、一次构建、双平台产物。Mac 和 Win 员工用的是同一个软件，不是"两个兼容的软件"。

## 一、三层统一（回答"框架不一样咋统一"）

**UI 统一**：员工界面 = 浏览器打开的公司工作台（服务端 Web）。Mac 的 Chrome 和 Win 的 Edge 打开是同一个页面、同一套操作。UI 只有一份代码。

**执行器统一**：本地小助手 = Go 语言单代码库，编译出两个产物：`company-agent.exe`（Win）和 `company-agent-macos`（Mac）。无 Python 依赖、无环境配置、双击就跑。本地能力（文件/命令/浏览器）是同一份代码，不存在两套实现。

**大脑统一**：Agent 推理逻辑（模型循环、工具调度、技能加载）100% 在服务端，一份 Python 代码。执行器只是"手"，不带"脑"，所以永远不会出现"Mac 版会做、Win 版不会做"。

行业对应：这就是浏览器模式——Chrome 有 Mac 版和 Win 版，但没人觉得"浏览器不统一"，因为渲染引擎一份代码、页面一份代码。

## 二、总体架构

```
┌──────────────── 公司服务器（Linux·Docker）────────────────┐
│ ① Web 工作台   一套 UI，双平台浏览器访问（任务/资产/看板） │
│ ② Agent 编排器 云端大脑：模型循环+工具调度+技能加载（Python）│
│    技能格式沿用 SKILL.md 约定（Hermes 体系直接迁移）       │
│ ③ LLM 网关     key 集中·按角色授权·记账到人·user_id 注入   │
│ ④ 控制面       FastAPI：auth/task/artifact/review/audit   │
│ ⑤ 数据面       SQLite(P0)→PG(20人+) + 产物存储 + 每日备份  │
└──────────────────────────┬───────────────────────────────┘
              TLS · 任务下发 / 工具调用 / 结果回传
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
  company-agent.exe   company-agent-macos   （未来 Linux 版）
  Win 员工本地执行     Mac 员工本地执行      同一代码库加一个构建目标
  文件·命令·浏览器·上报·心跳（Go 单二进制，双击运行）
```

## 三、执行器设计（Go，约 10-12 人日）

工具集（工具调用指令由服务端大脑下发）：
- 文件：读/写/移动/搜索（带路径硬边界：授权目录内，拒绝符号链接逃逸）
- 命令：执行 shell 命令（危险命令需员工在 Web 端二次确认）
- 浏览器：rod 或 playwright-go 驱动本机浏览器（登录态在员工本机）
- 上报：任务步骤/产物登记（幂等，断线重试队列）
- 心跳：在线状态、版本、队列长度
- 派活接收：inbox 拉取（服务端派活或员工自建）

非目标（砍掉，保统一）：执行器不做 UI（UI 全在 Web）、不做记忆存储（记忆在服务端）、不内置模型调用（大脑在服务端）。

分发：安装包 Win 用 NSIS、Mac 用 pkg/dmg；自动更新走服务端版本接口。

## 四、隐私分级路由（修正 V1.2 的红线表述）

诚实修正：文件内容本来就要发给模型 API（模型在云上），"不出员工电脑"从来只对公司服务器成立。分级处理：

- L1 本地任务（整理/重命名/格式转换）：纯工具指令，不过大脑，文件内容不出本机
- L2 标准任务（写方案/分析）：内容经 TLS 到服务端内存→转发模型 API→**只落摘要与产物引用，原文不落盘**，全程审计
- L3 高敏任务（客户合同等）：员工在 Web 上选"直连模式"，执行器直连模型 API（公司配的专用 key），内容完全不经过公司服务器
- 默认脱敏：上报的正则脱敏（手机/身份证/合同号）保留

## 五、Hermes 与 DSH 的重定位（不浪费现有资产）

- Hermes（我）：开发母机——技能开发、prompt 调优、编排器原型都在我这里先跑通，再下沉到服务端；技能体系（SKILL.md 格式、271 技能积累）直接迁移为服务端技能库的种子
- DSH（砺）：Win 侧执行器开发主力（Go）+ 双平台构建流水线（CI 出 exe/dmg）
- 两者的高级完整形态保留为"内部旗舰版"，主交付产品是统一执行器

## 六、API 契约与安全（继承 V1.2 第三、六章）

API v1 全保留（auth/heartbeat/tasks/steps/artifacts/skills/review/dashboard/inbox/model-route）。
客户端从"两个实现"变"一个实现"，契约测试降级为回归测试（成本更低）。
安全全继承：key 不落员工机、设备指纹+短期 token、审计全留痕、备份双副本、路径硬边界 30 行代码层。

新增一条：服务端大脑是单点 → P0 接受（重启断 30 秒，任务队列不丢）；P1 可上双实例热备（v1.1 的"每层可单独停机"验收口径不变）。

## 七、成本与里程碑（重估）

人日：执行器 Go 10-12 + 服务端编排器 10-12 + Web 工作台 8-10 + 控制面 8-10 ≈ **36-44 人日**（与 V1.2 持平，但省掉长期维护两套客户端的隐性成本）
分工：小慧=服务端三件（编排器+控制面+工作台）；砺=执行器+构建流水线；交叉互审不变。

W1 服务端骨架+API 全通（curl 走完一个任务闭环）
W2 编排器 MVP（一个技能从下发到执行到上报全链路）
W3 执行器双平台构建+文件/命令工具+路径边界
W4 Web 工作台 MVP（任务列表/时间线/产物/复核）
W5 双平台试点 2-3 台（1 Mac+1 Win）+ 断线重连演练
W6 加固+文档+AGENTS.md 落盘+20 人推广方案

## 八、代价与风险（直说）

1. 断网不能干活——V1.2 的"断网可跑"是伪卖点（模型在云上，断网本来啥也干不了），V1.3 正式放弃该表述，认账
2. 任务延迟多一跳网络——本地工具执行仍是毫秒级，模型推理本来就在云上，实际感知为零
3. Go 生态浏览器自动化选型（rod vs playwright-go）——W3 开工前 spike 两天定夺
4. 执行器功能面窄，需求膨胀风险低（没有 UI 就没有"顺手加个功能"的诱惑）

## 九、销售口径（给客户讲的一句话）

"每个员工电脑装一个几十 MB 的小助手，浏览器打开公司 AI 工作台，管理员在后台看所有人的任务和成果。Mac 和 Windows 装的是同一个软件。"
——一个产品、一个安装包故事、一句话讲完，这就是统一带来的交付红利。
